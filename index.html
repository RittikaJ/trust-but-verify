One good run tells us very little

Run A: the evidence supports the answer.

SAME TASK, DIFFERENT RUNS

An agent can choose a different tool, retrieve different evidence or recover differently from an error.

  1. Repeat the task.
  2. Inspect the steps.
  3. Verify the final state.

An evaluation is a repeatable check of the behavior we expect.

Opening04 / 16

What does “done correctly” mean?

WHAT DOES A CORRECT RUN REQUIRE?

  • The answer follows from the evidence.
  • The final state matches the task.
  • Permissions and approvals hold.
  • Cost and latency stay within budget.

These expectations become our evaluation contract.

Evaluation stack09 / 16

A useful judge has a narrow job

ONE CRITERION: CLAIM SUPPORT

PASS

Every material claim follows from the supplied evidence.

FAIL

At least one material claim lacks support.

Missing judge context? Return unjudgeable and route for review.

ILLUSTRATIVE JUDGE RESULT

{
  "verdict": "fail",
  "claim": "Source A supports the claim",
  "reason": "Passage addresses another issue",
  "evidence": "Relevant excerpt from source A"
}

A valid judge response can still be a wrong judgment.

Langfuse makes the loop inspectable

THE PRODUCTION FEEDBACK LOOP

  • Capture calls, results and versions.
  • Attach scores to a run or step.
  • Review failures and sampled passes.
  • Compare changes on verified cases.

Save our failed research run as a test case. Compare the next version against it.

The trace records what happened. The rubric decides what passed.

Where a human belongs in the loop

BEFORE EXECUTION

Should this
action happen?

  • Show the proposed action and evidence.
  • Ask for approval when the policy requires it.
  • Define what happens if nobody responds.
AFTER EXECUTION

Did this
run pass?

  • Review uncertain or disputed judgments.
  • Sample accepted runs for hidden failures.
  • Use expert feedback to improve the rubric.

A runtime approval and a review label serve different jobs.
